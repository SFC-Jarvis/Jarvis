# 作業の流れ

## 前提
- 各自の作業は発表の直前にまとめて行うことが多い。**main が更新されるのは発表の後**（各自の PR をレビューしてマージ）
- その代わり、作業ブランチはセッションの終わりに毎回 Push し、Draft PR を作成・更新する（/done）。
  他のメンバーは Draft PR で途中経過を見られる（main にはまだ入っていない）

## 1 期間（2 週間）の流れ
```
発表の翌日〜              期間中（各自のタイミング）                  発表の前日まで        発表後
───────────────────────────────────────────────────────────────────────────────────────────
① 全員で仕様決め   →   ② /start → 実装+テスト → /done（毎セッション）  →  ③ 全員でテスト  →  ④ /ship → 相互レビュー → マージ
  contracts/ を更新          （Draft PR が育つ）                           /report で報告文      → 次の期間は /start（最新 main から）
```

1. **仕様決め（期間の最初・全員）**: その期間に部品どうしがやりとりする内容を contracts/ に書き、小さな PR で先にマージする。以後は各自がその仕様とモックで単独開発できる
2. **実装**: `claude` を起動して `/start`。タスクの確認 → ブランチ作成（または再開）→ テストから実装。セッションの終わりに `/done`
3. **発表準備**: `/report` で自分の成果を Markdown に出し、Sota が `/report all` で全員分をまとめてスライド作成用のチャットに貼る
4. **マージ（発表後）**: `/ship` で Draft を解除してレビュー依頼。他の 1 人が Approve し、CI が全部通ったらマージ（Squash）。その後 `/sync` は不要で、次の期間は `/start` が最新 main から新しいブランチを作る

## レビューとマージのルール（GitHub で強制）
- main への直接 Push 禁止。PR 経由のみ
- マージ条件: **CI（ci-ok）がすべて成功** + **自分以外の 1 人が Approve** + 会話（コメント）がすべて解決済み + ブランチが最新
- 新しい Push があると Approve は取り消される（最後の Push をした人以外の Approve が必要）
- Owner（Sota）だけは必要なときにセルフマージ可（PR 経由のときのみ迂回可）。使ったら PR に理由を書く
- マージ方法は Squash のみ。PR タイトルがそのままコミットになるので Conventional Commits の形にする

## 仕様の変更
期間の途中で contracts/ を変える必要が出たら:
1. 影響を受ける担当者に連絡（チャット）
2. contracts/ の変更だけの小さな PR を作り、相手の Approve をもらってマージ
3. 各自 `/sync` で取り込む

## 複数の PC で作業するとき（例: 学校は Mac、家は Windows）
- PC を替える前に必ず `/done`（Push と PR の更新）
- 別の PC では `/start`。Push 済みの作業ブランチを取ってきて、PR の引き継ぎメモから再開する

## 衝突を減らすために
- 自分の分野のファイル（docs/tasks/<分野>.md を含む）以外は原則触らない。ただし `@自分` が付いたタスクの行は、他の分野のファイルでもチェックを更新してよい
- 共有ファイル（package.json、CI、CLAUDE.md、docs/CODING_RULES.md）の変更は単独の小さな PR にする
- 発表後のマージは「依存される側から」: contracts → tools → voice → web の順が目安
